# 验收与性能

## 验收标准

依次区分接口就绪、设备发现、Discover、Ask、Upload、解包落盘、发送端完成和文件一致性。HTTP200不自动代表系统相册已正确导入 Live Photo。两条引擎及 XOS 两个上层实现的验收分别记录，见各路线文档。

原图争议样本 `mmexport1736438611106.jpg` 为1182×1772、373450字节。小米源文件与经 iPhone 再发到 Mac 的样本逐字节一致，SHA256 `48b993cb54b4e9deef7334e7b65cd0f8cfaf42b2bfa3da0d9fdd39db1f066d60`。该样本没有压缩或缩放，用户也确认其他预览清晰度一致；不能推论所有云端原图或格式都不会发生分享端处理。

| MCS3 第一轮 | 0.478 | 0.286 |

MCS3保留，但远未完成性能目标。原版373450字节图片曾分别耗时16.316秒和6.899秒，包含不同会话阶段；一次4652575字节接收耗时14.179秒。150147066字节视频首轮被我们的进程更新中断，重试后用户要求停止，**没有完整大文件成功测速结果**。

## 为什么慢：证据与未知

约30秒视频抓包3818个发送数据段，311个重复起始序号（约8.1%），伴随拥塞窗口降至1及超时退避。该比例不是空口丢包率。

kprobe关联4679次提交/完成，提交返回都为0，表示skb未被退回，并不等于无线发送成功。status0/tries1的提交到完成延迟中位66.4ms、P95约830.5ms；另有status2且tries16事件。总延迟包括排队、无线发送、重试和完成上报，无法全部归因于队列等待。status2本身也不等于丢包，包含背景/广播情况。

现有 PASSTHRU 分支绕过常规状态统计，上层缺少足够反馈。AWDL窗口与排队/完成时序的配合是下一步方向，尚未证明唯一根因。应用解包不是当前最有力的瓶颈证据，也不能据此排除所有上层开销。

## 已撤回的实验

- guard从3 TU改12 TU：两轮发送0.396/0.254 MB/s，重试计数下降但吞吐不稳定，已恢复原库。有一次未成功替换库的测试已改名为control，不计入guard结果。
- pcap_inject后对大单播帧sleep1ms：发送0.200 MB/s，无改善，已撤回；该轮trace无效，不作延迟分析。
- MCS7只编译候选，未运行。
